# Team Standalone

oh-my-codex 0.21.14의 Team·Worker 절차를 바탕으로 만든 tmux용 개인 스킬이다. [MIT 라이선스](LICENSE)와 [원본 대비 차이·실행 방법](references/operations.md)을 참고한다.

**사용자가 팀 작업을 요청했을 때**, 일을 독립적으로 나누고 각 tmux 창의 Codex에게 맡긴다. 주 에이전트가 진행 상황을 확인하고 결과를 통합·검증한다. OMX를 설치하거나 Codex의 모델·설정·인증·자동 실행 연결을 바꾸지 않는다.

## 실행 전 확인

1. 합의된 목표·완료 기준과 프로젝트 지침을 읽는다. 이 스킬은 요구사항을 새로 정하거나 범위를 늘리는 절차가 아니다.
2. [실행 방법](references/operations.md)을 읽고 동봉된 `scripts/team.py`의 절대 경로를 확인한다. `preflight`로 Python·tmux·Codex 실행 경로와 필요한 명령 지원을 확인한다.
3. **해당 터미널의 Codex CLI가 허용된 모델·인증·권한으로 이미 작동하는지 확인한다.** 현재 대화와 별도 CLI의 설정이 같다고 가정하지 않는다. `preflight`는 모델 호출·로그인 성공·시험 규정 준수를 증명하지 않는다. 제공된 안내로도 이 조건을 확인할 수 없으면 부족한 조건을 알리고 실행을 보류한다.
4. 허용된 동시 실행 수와 사용량 안에서 인원을 정한다. 인원 지정이 없으면 독립적인 작업 두 개로 시작할 수 있는지 판단한다. 일 하나를 억지로 쪼개거나, 사용량이 줄 것이라고 약속하지 않는다.

tmux가 있어도 Codex CLI가 없거나 실행 권한이 없으면 이 방식은 사용할 수 없다. 이 스킬을 실행하기 위해 OMX·새 Codex·다른 모델을 설치하거나, 설정 파일·`CODEX_HOME`·모델 연결 환경변수를 변경하지 않는다. 권한 오류를 우회 옵션으로 해결하지 않는다.

## 작업 나누기

- 목표, 확인한 자료, 지켜야 할 조건, 모르는 부분을 짧게 기록하고 각 작업의 역할·수정 파일·완료 기준·검증 방법을 정한다.
- 한 번 실행하는 묶음은 서로 기다릴 필요가 없는 작업들로 구성한다. 앞 작업의 결과가 필요한 작업은 결과를 검증한 뒤 다음 묶음으로 실행한다.
- 같은 파일은 한 담당에게만 맡긴다. 공통 설정, 잠금 파일, 기록 문서 등의 수정은 주 에이전트에게 남기거나 별도 순서로 처리한다. 읽기 검토도 다른 작업이 수정 중인 파일을 완료본으로 판단하지 않도록 시점을 정한다.
- 작업 지시에는 담당 범위, 읽을 자료, 해야 할 검증, 남겨야 할 결과를 쓴다. 다른 담당의 변경을 되돌리지 말고, 범위 충돌이나 추가 요구는 보고하도록 한다.
- 프로젝트에 `docs/STATE.md`가 있으면 주 에이전트가 **이 팀 작업에 해당하는 자기 항목**을 갱신한다. 팀원들의 세부 결과는 실행별 기록에서 확인한다. 팀원에게 공유 STATE·HANDOFF·AGENTS의 수정을 나눠 맡기지 않는다. 이 파일들은 잠금이나 실시간 메시지 기능이 아니다.

## 시작과 진행 확인

1. 작업 계획 JSON을 프로젝트 안에 저장하고 `start --project ... --plan ...`로 시작한다. 보조 에이전트로 대체한 뒤 tmux 팀을 실행했다고 보고하지 않는다.
2. 반환된 실행 기록 경로와 실제 tmux 창 식별자를 보관한다. 시작 기록은 **프로세스가 시작됐다는 증거**이며 AI가 작업을 이해하거나 끝냈다는 증거가 아니다.
3. `status --run ...`와 담당별 기록·최종 응답으로 상황을 확인한다. 필요하면 `attach`로 해당 tmux 창들을 본다. 같은 실행을 확인하려고 `start`를 다시 호출하지 않는다.
4. 팀원은 자기 작업을 한 번 수행한 뒤 종료한다. 실행 중 지시를 바꾸려고 키 입력을 보내거나, 다른 팀을 만들거나, 같은 작업을 자동 재시도하지 않는다.
5. 주 에이전트는 독립적인 남은 일을 할 수 있지만 팀원에게 맡긴 파일은 동시에 수정하지 않는다. 인증·권한·모델 오류가 나오면 기존 설정을 고쳐 통과시키지 말고 원인을 보고한다.

## 결과 검증과 종료

- 종료 코드가 0이고 최종 응답이 있어도 `ready_for_review`일 뿐이다. 최종 응답에서 실제로 완료했는지, 막힌 조건은 없는지 읽는다.
- 주 에이전트가 변경 파일과 요구사항을 대조하고, 필요한 실행·테스트로 기대 결과와 실제 결과를 확인한다. 팀원 자체 보고만으로 완료 판정을 하지 않는다.
- 확인한 작업만 `review --verdict accepted --evidence ...`로 수용한다. 검증에 실패하면 `rejected`로 남기고 수정 범위를 정한다. 실행하지 못한 검증은 미확인으로 표시한다.
- 정상 종료는 모든 팀원의 프로세스 종료와 결과 수용, 필요한 통합 검증 이후에 한다. `shutdown`은 해당 실행의 tmux 세션을 닫고 작업 기록·결과는 보존한다. 명령 성공만으로 프로그램 완성이나 시험 제출 완료를 주장하지 않는다.
- 사용자가 중단했거나 실패로 실행을 끝내야 하면 `stop`으로 **해당 실행만** 중단하고 종료를 확인한 뒤 `shutdown`한다. 중단한 작업은 완료로 표시하지 않는다.

## 끊김·실패 처리

- 대화가 끊겨도 기존 실행 경로로 `status`를 먼저 확인한다. `attach`는 남아 있는 창을 보는 기능이며 끝난 AI 대화를 되살리는 기능이 아니다.
- 실행 상태가 불명확하거나 프로세스가 사라졌으면 완료로 추정하지 않는다. 남은 출력·파일·프로세스를 확인한다. 기존 담당이 더 이상 쓰지 않는다는 근거 없이 같은 파일을 새 담당에게 맡기지 않는다.
- 수정 후 다시 맡길 때는 기존 작업의 종료를 확인하고 새 계획·새 실행으로 남긴다. 이전 결과를 지우거나 실패를 성공으로 바꾸지 않는다.
- 종료 확인에 실패하면 남아 있는 실행 경로와 이유를 보고한다. 다른 tmux 세션, 사용자 터미널, OMX 상태, 별도 서버를 광범위하게 정리하지 않는다.

## 보고

사용자에게는 누가 무엇을 맡았는지, 실제 완료·검증한 내용, 남은 문제, 팀 종료 여부, 결과 기록 위치를 짧게 설명한다. 명령·프로세스 번호를 본문에 길게 나열할 필요는 없다.

이 버전은 **고정된 작업을 tmux에서 병렬 실행하는 방식**이다. 원본의 실시간 우편함·동적 작업 선점·자동 재배정·자동 작업 폴더 분리·혼합 AI 실행은 제공하지 않는다. 기능 차이는 [실행 방법](references/operations.md)에 명시한다.
