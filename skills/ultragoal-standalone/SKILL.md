# Ultragoal Standalone

합의한 큰 목표를 작은 작업으로 나누고, **작업 하나 실행 → 검증 → 기록·보고 → 사용자 지시 대기**를 반복한다. 사용자가 계속하라고 하면 다음 작업 하나를 진행한다. oh-my-codex 0.21.14의 Ultragoal을 바탕으로 했다. [기록 형식·Goal 연결·원본과의 차이](references/workflow.md), [MIT 라이선스](LICENSE)를 참고한다.

**tmux·OMX·별도 실행 프로그램은 필수가 아니다.** 현재 AI가 프로젝트 파일을 읽고 수정하고 필요한 검증을 실행할 수 있어야 한다. Codex Goal 도구가 있으면 전체 계획을 하나의 목표로 연결할 수 있다. 없으면 파일 기록을 따라 작업하지만, 대화 종료 뒤 자동으로 다시 실행되는 기능은 제공하지 않는다.

## 시작

1. 사용자 요청, 프로젝트 AGENTS, 합의 문서·구현 계획과 현재 변경을 읽는다. 목표·제외 범위·완료 기준을 확인한다. 이 스킬을 제작·설명·검토하라는 요청은 해당 목표의 실행 요청이 아니다. ‘계획만’ 요청이면 계획까지만 만들고 구현하거나 Codex 목표를 등록하지 않는다.
2. 합의된 계획이 있으면 재사용한다. 없으면 요청 범위 안에서 검증 가능한 작은 작업과 선행 관계를 정한다. 기능·구성·업무 규칙의 새 결정은 합의로 간주하지 않고 프로젝트의 확인 절차를 따른다.
3. [기록 형식](references/workflow.md)을 읽고 현재 프로젝트의 `.ultragoal/<실행-ID>/`에 `brief.md`, `goals.md`, `ledger.md`를 만든다. 기존 실행을 재개하는 요청이면 그 기록을 먼저 찾고 새 실행을 중복 생성하지 않는다. 기록은 실제 진행할 때 만들며 스킬 설치만으로 만들지 않는다.
4. 실제 제공된 도구와 사용자 요청으로 파일 모드 또는 Codex Goal 연결 여부를 정하고 알린다. 설정·모델·인증·권한을 바꾸거나 OMX·다른 스킬을 설치해서 조건을 맞추지 않는다. 도구 이름을 셸 명령으로 실행하거나 숨은 Goal 상태를 직접 수정하지 않는다.

## 실행과 기록

- 현재 진행 중인 작업을 먼저 확인한다. 한 번에 `goals.md`의 작업 항목 하나만 수행한다. 그 항목 안에서 도움이 될 때 보조 에이전트를 쓰되, 다음 항목을 미리 시작하거나 맡기지 않는다. 작은 작업 하나가 곧 별도 에이전트 하나라는 뜻은 아니다.
- 실행 전에 완료 기준과 검증 방법을 읽고 상태를 ‘진행 중’으로 바꾼다. 요청 범위 안에서 구현하고, 실제 입력·기대 결과·실제 결과 또는 적절한 검증 명령·출력을 확인한다.
- 결과물과 검증 근거를 저장한 뒤에만 해당 작업을 ‘완료’로 바꾼다. 실행하지 못한 검증은 미확인이다. 실패하면 원인을 짚고 수정 범위를 정해 다시 검증한다. 같은 실패를 새 근거 없이 반복하거나 완료 기준을 낮추지 않는다.
- 작업 시작·검증·실패·범위 변경·중단 때 `goals.md`의 현재 상태를 갱신하고 `ledger.md` 끝에 실제 근거를 추가한다. 두 기록을 다시 읽어 일치를 확인한다. 기록 파일 자체가 동작 성공을 증명하지는 않는다.
- 한 작업의 구현·필요한 수정·검증·기록이 끝나면 결과와 다음 작업을 보고하고, 전체 완료 전에는 ‘계속 대기’로 남겨 이번 응답을 끝낸다. 필요한 결정·권한·자료가 없어 막혔을 때도 이유와 해결 조건을 보고하고 멈춘다. 다음 작업을 시작하거나 백그라운드로 남겨 두지 않는다. 사용자가 중단하면 관련 실행의 종료를 확인하고 미완료 상태를 보존한다.
- 사용자가 ‘계속’, ‘다음 작업 진행’처럼 명시적으로 요청하면 상태를 확인하고 다음 작업 하나만 진행한 뒤 다시 보고하고 멈춘다. 설명 요청이나 결과에 대한 질문을 다음 작업 진행 지시로 해석하지 않는다.

## 담당과 재개

- 한 실행의 세 기록은 **주 에이전트 한 명만** 수정한다. 보조 에이전트는 담당 파일과 검증 결과를 보고한다. 다른 세션이 쓰는 실행을 임의로 인수하지 않는다. 이 기록은 파일 잠금이나 세션 간 연락 기능이 아니다.
- 프로젝트에 STATE 규칙이 있으면 자기 작업 항목에 이 실행의 요약·기록 경로·인수 가능 여부를 남긴다. STATE 전체를 이 계획으로 바꾸거나 다른 담당의 항목을 수정하지 않는다. HANDOFF는 기존 프로젝트 규칙과 사용자의 인계 요청을 따른다.
- 재개할 때 실제 프로젝트 경로, 기존 담당의 종료·인수 가능 근거, 합의 문서, 세 기록, 결과물과 검증 증거를 대조한다. 오래된 기록만 보고 기존 담당이 멈췄다고 추정하지 않는다.
- 기록이 불일치하거나 이전 검증 이후 파일·완료 기준이 바뀌었으면 영향받는 작업을 재검증한다. 확인 전에는 완료로 유지하지 않고 이유를 남긴다. 복구 결과는 새 이력으로 추가하고 과거 실패·검토 결과를 지우지 않는다.

## 계획 수정

작업 추가·분할·순서 변경·설명 수정·기존 작업 대체가 필요하면 이유와 근거를 기록한다. 단순한 구현 순서 조정은 합의 범위 안에서 할 수 있지만 기능·완료 기준·제외 범위가 바뀌면 먼저 사용자의 선택을 받는다. 같은 변경 요청을 이미 반영했는지 확인한다.

작업 ID를 재사용하거나 기존 작업을 지우지 않는다. 대체된 작업에는 ‘대체됨’과 후속 ID를 남기고 의존 관계를 수정한다. 대체는 완료가 아니며, 대체 작업이 검증되기 전에는 관련 후속 작업을 완료로 취급하지 않는다. 변경의 영향을 받는 이전 검증도 다시 확인한다.

## 최종 완료 확인

개별 작업이 끝나도 전체 완료는 아래 확인 뒤에 판단한다. 마지막 구현 작업 뒤에도 먼저 보고하고 멈추며, 이 최종 확인은 다음 진행 요청을 받아 별도 작업 항목으로 수행한다. 검토에서 새 수정 작업이 생기면 기록·보고한 뒤 다음 진행 요청을 기다린다.

1. **변경 정리:** 이번 변경에서 불필요하게 추가한 코드·중복·사용하지 않는 부분을 확인하고 필요한 부분만 정리한다. 무관한 리팩터링이나 새 기능을 추가하지 않는다. 별도 `ai-slop-cleaner` 스킬 설치는 필요 없다.
2. **재검증:** 정리·수정의 영향을 받는 검증과 필요한 통합 검증을 실행한다.
3. **중요 규칙 대조:** 합의한 구조·계산·권한·오류 처리 등의 중요한 규칙이 실제 구현과 검증으로 지켜지는지 확인한다. 해당하지 않는 항목은 이유와 함께 표시한다.
4. **독립 검토:** 구현을 작성하지 않은 검토자에게 구현·회귀 위험 검토와 구조·업무 규칙 검토를 각각 맡긴다. 가능한 경우 별도 보조 에이전트 두 명을 사용한다. 역할 이름이 없어도 두 관점을 명시한다. 자기 검토를 독립 검토라고 쓰지 않는다.
5. **지적사항 해결:** 필요한 수정 작업을 기존 지적사항과 연결해 기록하고, 수정 후 영향받은 검증과 검토를 다시 받는다. 독립 검토를 받을 수 없으면 결과물·자기 검토를 남기되 전체 상태는 ‘검토 대기’다. 전체 완료나 Codex Goal 완료로 처리하지 않는다.

모든 유효한 작업과 최종 확인을 통과해야 전체 ‘완료’다. Goal을 연결했다면 아래 참조의 도구 절차로 실제 완료를 확인한 뒤 최종 기록을 남긴다. 파일 모드에서는 Goal 도구를 호출했다고 주장하지 않는다.

## 보고

사용자에게 완료·미완료 작업, 실제 검증 결과, 남은 결정·검토, 기록 위치, Goal 연결 여부를 짧게 알린다. ‘구현은 끝났지만 독립 검토가 남았다’처럼 상태를 구분한다. 자동 계속 실행·동시 수정 보호·원본과 같은 기능이나 성능을 보장하지 않는다.
