# 기록 형식과 실행 조건

## 필요한 것

- 필수: 프로젝트 파일을 읽고 수정하는 AI 환경, 해당 과제의 검증을 실행할 수 있는 도구·권한. 이 스킬 자체는 Python·tmux·OMX 설치를 요구하지 않는다.
- 선택: Codex의 `get_goal`, `create_goal`, `update_goal` 도구. 실제 세션에 제공되어야 사용할 수 있다. `/goal`이 메뉴에 있다는 이유만으로 세 도구를 호출할 수 있다고 추정하지 않는다.
- 원본의 최종 검토 유지: 구현자와 독립된 검토. 보조 에이전트가 없으면 별도 검토 결과를 받을 때까지 ‘검토 대기’로 남긴다.
- Team Standalone을 별도로 사용한다면 그 스킬의 tmux·Python·Codex CLI 조건이 추가된다. Ultragoal이 Team을 자동 실행하지 않는다.

## 실행마다 남기는 세 기록

프로젝트 안에 다른 실행과 겹치지 않는 `.ultragoal/<실행-ID>/` 폴더를 만든다. 예를 들어 실행 ID는 `20261029-csv-validation-01`처럼 정할 수 있다. 재개할 때는 기존 ID와 실제 절대 경로를 사용한다. 이름이나 경로만으로 인수 권한이 생기지는 않는다.

### brief.md — 왜 무엇을 하는지

다음 내용을 처음에 기록한다. 합의 변경 시 현재 내용과 이력을 함께 갱신한다.

- 실행 ID, 실제 프로젝트 경로, 담당 식별자와 인수 가능 여부·근거.
- 사용자 요청과 합의 문서·기존 구현 계획 위치.
- 목표, 제외 범위, 완료 기준, 지켜야 할 구조·업무 규칙.
- 확인하지 못한 내용과 필요한 결정.
- 실행 방식: 파일 모드 / Codex Goal 연결. 연결했다면 목표의 정확한 objective와 도구가 반환한 식별 정보, 확인 시각·근거 위치.

### goals.md — 지금 어디까지 했는지

맨 위에는 전체 상태, 현재 작업 ID, 다음 행동, 최신 확인 시각을 적는다. 전체 상태는 `계획 / 실행 중 / 계속 대기 / 막힘 / 검토 대기 / 중단 / 완료`를 사용한다. 작업 하나를 검증·보고하고 전체 완료 전에는 ‘계속 대기’와 다음 작업 ID를 적는다. 사용자의 다음 진행 요청 전에는 그 작업을 시작하지 않는다.

그 아래 각 작업을 다음 형식으로 적는다. 값은 실제 요청과 확인 결과로 채운다. 예시 작업을 실전 요구사항으로 복사하지 않는다.

```markdown
## G1. 합의된 입력 검증 구현
- 목표: SPEC에서 정한 입력 검증을 구현한다.
- 선행 작업: 없음
- 완료 기준: SPEC의 정상·누락 입력에 대해 합의한 결과를 반환한다.
- 상태: 대기
- 결과물·검증 근거: 아직 없음
- 다음 행동: SPEC의 입력 규칙과 기존 코드를 확인한다.
```

`G1`은 첫 번째 작은 작업의 식별 번호다. 번호 자체에 단계·우선순위 의미는 없으며 한번 정하면 재사용하지 않는다. 각 작업의 상태는 다음처럼 구분한다.

- **대기:** 아직 시작하지 않음.
- **진행 중:** 실제로 수행하고 있음.
- **막힘:** 필요한 자료·결정·권한 등이 없어 진행할 수 없음. 해결 조건을 함께 기록.
- **검증 실패:** 실행했으나 완료 기준을 만족하지 못함. 실패 근거와 수정 방향을 기록.
- **완료:** 결과물이 있고 완료 기준을 실제로 검증함.
- **대체됨:** 다른 작업으로 교체됨. 대체 작업 ID·이유·영향받은 선행 관계를 기록. 성공으로 집계하지 않음.

작업 사이 선행 관계에 순환이나 없는 ID가 있으면 먼저 고친다. 선행 작업이 막힘·검증 실패·대체됨인 상태를 선행 완료로 취급하지 않는다. 기준 변경으로 기존 완료 근거가 무효가 되면 해당 작업과 영향받은 후속 작업을 다시 확인 대상으로 표시한다.

마지막에는 **최종 확인**을 둔다. 변경 정리, 재검증, 중요한 규칙 대조, 독립 구현 검토, 독립 구조·업무 규칙 검토별로 수행자·결과·증거 위치·남은 문제를 기록한다. 아직 하지 않은 것은 미확인으로 쓴다. 모든 개별 작업이 완료여도 이 확인이 남아 있으면 전체 완료가 아니다.

### ledger.md — 무엇을 확인하고 바꿨는지

새 기록을 맨 아래에 추가하고 과거 기록은 덮어쓰지 않는다. 잘못 기록한 사실은 정정 이력을 추가한다. 각 기록에는 다음을 포함한다.

- 시각, 해당 작업 ID 또는 전체 실행.
- 이전 상태 → 새 상태, 바뀐 내용과 이유·사용자 합의 근거.
- 실제 검증 명령 또는 확인 방법, 기대 결과와 실제 결과, 저장한 근거 위치.
- 막힌 조건·후속 작업·검토 결과. Goal 도구를 호출했다면 필요한 응답 근거.

인증 정보나 전체 대화를 복사하지 않는다. 결과물과 긴 출력은 실제 파일에 저장하고 필요한 부분만 인용한다. 파일을 읽고 쓴다는 것만으로 동시 수정 잠금·이력 위변조 방지·자동 재개 기능이 생기지 않는다. 기록 불일치는 결과물·검증·현재 담당을 확인해 복구하고 정정 이력을 남긴다.

## Codex Goal 연결

스킬을 설명·설치·수정하는 중에는 Goal을 만들지 않는다. 계획만 요청한 경우도 같다. 실제 실행에서 **사용자가 Codex 목표 등록과 작업마다 일시정지를 명시적으로 요청했고 세 Goal 도구가 제공될 때만** 다음 절차를 사용한다. 목표 등록만 요청했다면 작업마다 멈추는 방식을 설명하고 확인받기 전에는 Goal을 연결하지 않는다. 일반 작업 요청에서 목표 등록을 추정하지 않는다.

1. `get_goal`로 실제 상태를 읽는다. 새 목표를 만들 수 있으면 계획 전체를 가리키는 하나의 objective로 `create_goal`을 호출한다. 예: “<절대 경로>/brief.md와 goals.md의 합의 범위 및 최종 검토 기준을 모두 충족한다.” 사용자 요청에 없는 예산은 지정하지 않는다.
2. 이미 같은 실행의 목표가 있으면 실제 objective·기록·상태가 일치하는지 확인한다. 작업 경계에서 멈춘 경우 사용자의 다음 진행 요청과 Goal의 재개 상태를 확인한 뒤 이어간다. 다른 목표가 남아 있으면 수정·완료·삭제하거나 새 목표로 덮어쓰지 않는다. 현재 실행과 연결되지 않았음을 보고한다. 새 목표 생성 허용 여부는 도구의 현재 규약을 따른다.
3. 작은 작업 하나를 완료할 때마다 증거를 파일에 남기고, 연결된 Goal의 최신 상태를 `get_goal`로 확인해 기록한다. 중간 작업을 끝냈다고 전체 Goal을 완료하지 않는다. 전체 목표의 안정적인 파일 경로를 유지하고 매 작업마다 새 Goal을 생성하지 않는다.
4. 최종 검토까지 통과한 뒤 `update_goal({"status":"complete"})`를 호출하고 다시 `get_goal`로 실제 완료 상태를 확인한다. 성공이 확인되지 않으면 ‘작업 검증 완료, Goal 상태 반영 미확인’으로 구분하고 재개 시 정합성을 확인한다. 요청한 예산이 있었다면 도구가 반환한 최종 사용량을 보고한다.
5. 일시정지·막힘·재개·예산 제한은 **현재 Goal 도구의 조건을 그대로 따른다.** 파일의 ‘막힘’과 native Goal의 `blocked`는 별개다. 사용자가 ‘작업마다 보고하고 멈춰’라고 명시한 경우, 전체 완료 전 작업 경계마다 연결된 Goal도 `update_goal({"status":"paused"})`로 일시정지하고 실제 상태를 확인해 보고한다. 그 요청 없이 임의로 일시정지하지 않으며, 파일의 ‘계속 대기’만으로 활성 Goal이 멈췄다고 보고하지 않는다. 재개는 해당 환경이 지원하는 사용자 절차를 따르고, 도구가 금지한 재개·예산 변경·숨은 상태 수정을 하지 않는다. 사용자가 중단했거나 예산·사용량 제한에 도달한 Goal을 파일 모드로 바꿔 우회하지 않는다.

사용자가 Goal 등록을 요청하지 않았거나 처음부터 도구가 없는 경우는 파일 모드로 수행할 수 있다. 연결하려던 Goal 조회에 실패했거나 기존 목표의 상태·소유 관계가 불명확하면 임의로 연결·해제하지 말고 상황을 보고한다. 도구가 없다는 사실과 기존 목표의 중단·한도를 혼동하지 않는다. 파일 모드의 기록은 다음 대화가 이어받는 근거이며 자동 실행 장치가 아니다.

## 원본 대비 범위

| 원본 역할 | 독립형에서 처리하는 방식 |
| --- | --- |
| brief, goals.json, ledger.jsonl | 실행별 brief.md, goals.md, ledger.md로 요청·현재 상태·변경 이력 보존 |
| create-goals / complete-goals / checkpoint | AI가 합의된 계획을 분해하고 실행·검증·기록 절차 수행 |
| 다음 작업으로 계속 진행 | 작업 하나마다 보고하고 멈춤. 사용자의 다음 진행 요청이 있어야 다음 항목 수행 |
| 전체 계획을 하나의 Codex Goal로 연결 | 사용자 요청과 도구 지원이 있을 때 유지. 파일 모드는 별도로 표시 |
| 계획 변경 명령과 검증 | 변경 이유·합의·ID·의존 관계를 확인하고 이력 추가. 명령 수준의 강제 검사·중복 방지는 없음 |
| 최종 cleaner·검증·구조 규칙·독립 검토 | 정리와 검증은 지침으로 수행하고 독립 검토 결과 요구. 다른 OMX 스킬 설치 불필요 |
| 상태 잠금·원자적 갱신·세션 소유 검증 | 재현하지 않음. 단일 작성자와 인수 확인 절차로 운영 |
| hooks·HUD·자동 팀 연동 | 미포함. 선택적인 별도 Team 작업만 가능 |
| 중단 후 재개 | 파일·담당·현재 증거를 다시 확인. 파일만으로 자동 재시작하지 않음 |

이 버전의 완료 조건은 AI가 따라야 하는 절차다. 별도 실행기가 강제로 검증하는 기능은 아니다. 원본과 동일한 자동화·동시성 보호·성능을 보장하지 않는다.
