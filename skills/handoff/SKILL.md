# Handoff

사용자가 handoff 또는 인계 기록 작성을 요청했을 때 실행한다.
프로젝트의 HANDOFF.md에 인계 시점의 실제 상황을 기록한다.
이 스킬의 작성 지침을 HANDOFF에 복사하지 않는다.

## 작성 원칙

- “다음 세션의 AI는 이 파일 외에 아무것도 모른다”고 가정한다.
  여기서 이 파일은 HANDOFF.md다.
  목표·합의·현재 상황·다음 행동을 이해할 수 있게 설명하고,
  더 필요한 자료는 실제 파일 위치와 읽어야 하는 이유를 안내한다.

- 대화에만 존재하는 초안·코드는 HANDOFF를 쓰기 전에 먼저 파일로 저장한다.
  HANDOFF는 포인터지 저장소가 아니다.
  긴 코드나 초안 전체를 붙이는 대신 저장 위치와 용도를 적는다.
  승인 전인 내용은 ‘미승인 초안’, 실행하지 않은 코드는 ‘미검증’으로 표시한다.

- 새 엔트리는 문서 제목 바로 아래, 기존 기록보다 위에 추가한다.
  작성 시각·작업명·담당을 표시하고 과거 엔트리는 지우거나 고쳐 쓰지 않는다.
  이전 결정을 바꿨다면 새 엔트리에 변경 내용과 이유를 적는다.
  다른 작업의 기록도 보존한다.

- 사실·추측·미확인을 구분한다.
  파일이 있다는 이유만으로 구현·검증·승인이 끝났다고 판단하지 않는다.
  키·토큰·개인정보는 기록하지 않는다.

## 작성 전 확인

1. 인계할 작업과 실제 작업 폴더를 확인한다.
2. AGENTS.md, 기존 HANDOFF.md, docs/STATE.md와 관련 파일을 읽는다.
   없는 문서나 확인하지 못한 내용은 있다고 가정하지 않는다.
3. 대화에만 남은 초안·코드를 저장한다.
4. 실제 변경 파일과 확인된 실행 결과를 대조한다.
   Git을 사용한다면 브랜치와 미커밋 변경도 확인한다.
5. 아래 기준으로 인계 시점의 진행 상태를 판단한다.

인계 기록을 작성하기 위해 남은 기능을 임의로 구현하거나,
여섯 단계를 모두 완료하려고 하지 않는다.

## 1~6단계의 뜻과 완료 판단

단계별 상태는 handoff를 작성하는 AI가 실제 작업과 확인 근거를 보고 판단한다.
사용자가 단계 번호나 전환을 지정할 필요는 없다.
이 단계 구분은 인계 시점의 진행 상황을 설명하기 위한 것이며, 구현 순서를 강제하지 않는다.
판단할 근거가 부족하면 ‘미확인’으로 남긴다.

### 1. 문제 파악
누구의 어떤 문제를 해결하려는지 파악하는 단계다.
현재 업무 방식·주요 불편·관련 사람·주요 제약을 정리하고,
확인된 사실과 남은 질문을 구분했는지 확인한다.
근거가 되는 인터뷰 원문이나 정리 기록의 위치를 남긴다.

### 2. 범위 확인
이번에 만들 것과 만들지 않을 것, 목표와 완료 기준을 정하는 단계다.
데이터·권한·환경 제약을 포함해 진행할 범위를 사용자에게 확인받았는지 본다.
실무자가 확인한 사실과 사용자가 선택한 내용은 구분한다.
범위를 결정하는 데 필요한 선택이 남아 있다면 완료로 표시하지 않는다.

### 3. 기본 실행
프로그램의 최소 구성이 실제 환경에서 실행되는지 확인하는 단계다.
실행 명령·접속 위치·정상 결과가 확인됐는지 본다.
코드나 설정 파일을 만들기만 한 상태는 실행 완료가 아니다.

### 4. 핵심 흐름 구현
입력부터 처리와 최종 결과까지 이어지는 핵심 기능을 만드는 단계다.
합의한 핵심 흐름을 실제로 한 번 이상 실행했는지 확인한다.
화면만 있거나 중간 처리만 구현된 경우에는 남은 연결을 적는다.

### 5. 결과 검증
만든 기능이 합의한 완료 기준을 충족하는지 확인하는 단계다.
실제 입력·기대 결과·실제 결과를 비교하고,
관련된 빈 입력·중복·형식 오류·외부 실패도 확인했는지 본다.
완료 기준을 충족했다는 근거가 있어야 완료로 표시한다.
남은 오류와 확인하지 못한 동작은 별도로 적는다.

### 6. 제출 준비
다른 사람이 실행·사용할 수 있도록 설명과 제출물을 정리하는 단계다.
사용 설명서에 실제 실행법·사용법·한계를 적었는지,
그 방법으로 다시 실행했는지,
실제 제출 요구에 맞는 파일·경로·미리보기를 확인했는지 본다.
제출 준비 완료와 실제 제출 완료는 구분해서 기록한다.

각 단계는 ‘완료 / 진행 중 / 미진행 / 미확인 / 해당 없음’과
짧은 근거·남은 일을 함께 적는다.
해당하지 않는 단계에는 이유를 적는다.
자기 작업 하나가 끝났다는 이유로 프로젝트 전체 단계를 완료 처리하지 않는다.

## 새 인계 기록에 남길 내용

### 인계 대상과 당시 상태
작성 시각, 작업명, 담당, 작업 폴더, 브랜치가 있다면 브랜치.
현재 하는 일과 인수 가능 여부.
이 내용이 인계 작성 당시의 상태임을 명시한다.

### 목표와 합의
해결하려는 문제, 만들 것·만들지 않을 것, 완료 기준과 제약.
중요한 결정과 이유, 아직 확인받지 않은 내용.
관련 합의·설계 문서가 있다면 위치를 안내한다.

### 단계별 진행 상황
위 1~6단계의 실제 상태와 근거를 짧게 정리한다.
단계 설명이나 작성 지침 자체를 다시 붙이지 않는다.

### 끝낸 일과 남은 일
변경한 파일, 확인한 결과와 근거, 진행 중인 작업, 막힌 점.
실패한 시도와 확인된 원인, 반복하지 않아야 할 시도.
원인이 밝혀지지 않았다면 추측을 확정된 원인처럼 쓰지 않는다.

### 이어가기 위한 자료와 실행법
먼저 읽을 파일과 이유, 저장한 초안·코드의 위치와 상태.
실행·검증 명령, 필요한 입력과 환경 설정, 정상 결과.
환경 변수는 이름만 적고 비밀 값은 적지 않는다.

### 다음 행동
다음 AI가 가장 먼저 할 일을 구체적으로 적는다.
먼저 확인받아야 할 결정이나 필요한 자료가 있으면 함께 적는다.
작업 재개 전 최신 AGENTS와 STATE를 읽고 인수 조건을 확인하도록 안내한다.

## 저장과 마무리

- 저장 직전에 최신 HANDOFF를 다시 읽고 새 엔트리를 맨 위에 추가한다.
- 안내한 파일이 실제로 존재하는지, 과거 기록이 보존됐는지 확인한다.
- handoff를 작성했다는 이유만으로 작업을 ‘인수 가능’으로 바꾸지 않는다.
  AGENTS의 저장·관련 수정 작업 종료 확인 조건을 따른다.
- 사용자에게 저장 위치와 다음 첫 행동을 짧게 보고한다.
